# Redis 缓存与令牌登录

## Redis 的数据结构与本项目用途

Redis 提供多种数据结构：String 用于验证码、对象缓存和计数器；Hash 用于存储对象的多个字段，本项目用它保存登录用户的 id、昵称和头像；List 可实现简单的队列；Set 用于去重集合，本项目用它实现关注列表和共同关注；ZSet 带分数，用于点赞排行、按时间排序；Geo 用于附近店铺查询；Bitmap 用于签到统计；HyperLogLog 用于估算 UV。选择合适的数据结构比把数据都序列化成 String 更省内存，也更方便做原子操作。

## 缓存模式

最常用的是 Cache Aside（旁路缓存）。读操作：先查缓存，命中直接返回；未命中则查数据库，把结果写回缓存并设置过期时间。写操作：先更新数据库，再删除缓存，而不是更新缓存。删除缓存的原因是并发写场景下两次更新缓存的顺序可能错乱，留下旧值；删除后下一次读会自然回填最新数据。删除缓存也可能失败，可以配合重试或消息队列补偿，进一步降低不一致的时间窗口。如果业务能接受短暂不一致，这已经足够；要求强一致时缓存只会成为负担。

## 缓存穿透、击穿与雪崩

缓存穿透指查询的数据在数据库里也不存在，请求绕过缓存每次都打到数据库，常见于恶意用不存在的 id 刷接口。对策包括：缓存空值并设置较短的过期时间；使用布隆过滤器提前判断 key 是否可能存在；在入口做参数校验和限流。

缓存击穿指某个热点 key 恰好过期，瞬时大量请求同时打到数据库。对策是互斥重建：只允许一个线程查库并回填缓存，其余线程短暂等待后重试；或者使用逻辑过期，缓存中保存过期时间但物理上不过期，发现逻辑过期后异步重建并先返回旧值。

缓存雪崩指大量 key 在同一时刻过期，或者 Redis 整体不可用，导致请求全部压到数据库。对策是给过期时间加随机值打散、Redis 做主从加哨兵或集群保证高可用、对数据库访问做限流和降级、使用本地缓存作为多级缓存的第一层，并在启动时做缓存预热。

## 本项目的令牌登录流程

用户提交手机号和验证码登录后，后端校验验证码，生成一个随机的 token（通常用 UUID 去掉横线），把用户信息以 Hash 结构写入 Redis，key 形如 login:token:{token}，并设置 30 分钟的过期时间。接口返回 token，前端在后续请求的 authorization 请求头中携带它。

请求进入后，RefreshTokenInterceptor 从请求头取出 token，查询 Redis 中的 Hash；如果存在，把数据转换成 UserDTO 放入 ThreadLocal，并刷新这个 key 的过期时间，实现「活跃用户自动续期」；取不到用户时它直接放行，不在这里拦截。随后 LoginInterceptor 检查 ThreadLocal 中是否有用户，为空就返回 401 并中断请求。这种分层设计让需要登录的接口和公开接口可以共用同一套 token 刷新逻辑。

退出登录时删除对应的 login:token:{token}，该 token 立即失效，但其他设备上的 token 不受影响。token 属于会话凭证，不应该放在 URL 里，生产环境必须使用 HTTPS，并且不要在日志中打印完整 token。

## 分布式锁与秒杀

分布式锁的基本写法是用 SET key value NX EX 原子地加锁并设置过期时间，value 使用一个唯一标识（例如 UUID 加线程 id）。释放锁必须用 Lua 脚本先比较 value 再删除，否则可能删掉别人后来加的锁。Redisson 提供了可重入锁和看门狗自动续期，适合业务执行时间不确定的场景。

秒杀场景下，先用 Lua 脚本在 Redis 中原子地判断库存并扣减，成功后再把下单请求放入队列或 Redis Stream 异步创建订单，从而把数据库压力削峰。一人一单可以在 Lua 中通过 setnx 或集合判断，保证原子性。

## 其他要点

Redis 执行命令的主流程是单线程的，所以单条命令具有原子性；但多条命令的组合并不是原子的，需要 Lua 脚本、MULTI 事务或分布式锁。Redis 6 起网络 IO 使用多线程，命令执行仍然是单线程。过期键采用惰性删除加定期删除，内存达到 maxmemory 后按 maxmemory-policy 淘汰，常见策略是 allkeys-lru。持久化有 RDB 快照和 AOF 追加日志两种，可以同时开启。
